## Phase 1: Contract Modeling & Design

### `contract.aztec-spec.yaml`
- Use the [Aztec/Noir meta-language](../docs/aztec-contract-meta-language.md).  
- Populate metadata, contract description, roles, state, notes, events, functions, flows, invariants, external interfaces, sequence diagram references, test guidance, and annotations.  
- Validate schema before saving (maintain stable key ordering for diffs).  
- Highlight unresolved items with `[NEEDS CLARIFICATION: ...]` for follow-up.

### `flows.md`
- Summarize each flow defined in YAML `flows` section.  
- Include privacy transition tables (public→private, etc.), notes created/consumed, events emitted, and references to functions.  
- Link to diagrams by ID.

### `sequence-diagrams/`
- For each critical flow, provide a Mermaid file `*.mmd` or linked asset.  
- Ensure IDs match entries in YAML and flows.md (`sequence_diagrams` section).

### `btt.seed.tree`
- Convert YAML `functions`, `flows`, `invariants`, and `test_guidance` into an initial BTT tree.  
- Use `Contract::function` roots where multiple entry points exist.  
- Annotate comments for rationale (prefix with `//`).  
- This file primes `/noir-treegen`.

### `test-plan.md`
- Derive scenarios from YAML `test_guidance`, `flows`, and invariants.  
- Track coverage targets (happy, negative, fuzz) and acceptance criteria.  
- Map tests to expected directories (`tests/unit`, etc.) and required fixtures/utilities.

**Exit Criteria**: All artifacts drafted, schema validated, transitions described, BTT seed consistent with YAML, test plan covering scenarios.

## Phase 2: Task Planning Approach (for `/tasks` command)
- Input sources: `contract.aztec-spec.yaml`, `flows.md`, `btt.seed.tree`, `test-plan.md`.  
- Generate tasks in the following order:  
  1. Implement missing fixtures/utilities required by test-plan.  
  2. Scaffold tests based on BTT branches (unit → integration → fuzz → security).  
  3. Implement contract/library functions from YAML spec.  
  4. Validate invariants and events per test-plan.  
- Mark tasks ready for parallelization when they touch disjoint modules/tests.  
- Ensure tasks include verification steps (run targeted tests, regenerate tree, etc.).

**NOTE**: `/plan` only documents this strategy; `/tasks` creates `tasks.md` later.
